## What changed

`CMakeLists.txt` sets the macOS defaults before `project()`: `CMAKE_OSX_ARCHITECTURES` to
`arm64;x86_64` and `CMAKE_OSX_DEPLOYMENT_TARGET` to `11.0`, only when neither the cache nor the
environment already holds a value. The test is on `CMAKE_HOST_APPLE`, not `APPLE`: before
`project()` CMake has not identified the target system yet, so `APPLE` is empty, while
`CMAKE_HOST_APPLE` is set by CMake itself at start-up; I verified with a scratch project that on
this Linux machine `CMAKE_HOST_UNIX` is `1` and `CMAKE_HOST_APPLE` and `APPLE` are both empty at
that point. The macOS build is native, so the host is the target. The two sanitizer options are
refused with `FATAL_ERROR` when `CMAKE_SYSTEM_NAME` is not `Linux`. The warning options are chosen
by compiler: `/W4` under `MSVC`, the GCC-style set otherwise, in a `KCF_WARNING_OPTIONS` variable
that `kcf_engine` takes. `FORMATS` gains `AU`. The comment on the disabled MIDI CC emulation cited
`docs/architecture.md`, a file that no longer exists; the README does not document that behaviour
either (I grepped for it), so the comment now stands on its own and points at the REAPER `panic`
stage in the development guide. `THIRD_PARTY_NOTICES.md` cited the same dead file for the
mathematical definitions and now names the README's "How it works" section. The version is 1.4.0.

`tests/CMakeLists.txt` keeps `kcf_engine_tests` outside any guard with its own compiler-aware
warning options, and puts the three Linux-only executables, their `find_package(PkgConfig)`,
`pkg_check_modules` and `X11`, `rt`, `pthread` links inside `CMAKE_SYSTEM_NAME STREQUAL "Linux"`.

`plugin/Presets.cpp` adds the `Application Support` component under `JUCE_MAC` only, after the
`KCF_PRESET_DIR` check, which still wins on every platform. The edit sits after the file's only
assertion site, so no `__LINE__` moved.

`run` computes its default target list from `uname -s` (the three Linux-only test targets on
Linux, `KickCrafterFable_AU` on macOS, neither on Windows), appends `.exe` to the test binaries
under `MINGW*` and `MSYS*`, and gains `dist`. `DISPLAY` and `KCF_DISPLAY` keep their defaults on
every platform: `set -u` would otherwise trip on them, and exporting them is harmless where
nothing reads X11. Nothing bash 4 was added; the script already had none.

`tools/run-logged.sh` defines the `sha256` helper (`sha256sum` when it exists, `shasum -a 256`
otherwise) and computes the manifests with a `while read` loop feeding it instead of `xargs
sha256sum`. I checked that the loop yields the same hash as the old pipeline on the current tree
(both lines print hash, two spaces, path). The log stamp's nanoseconds come from `date +%N` when
the output is digits and are `000000000` otherwise, because BSD `date` prints a literal `N`; on
Linux the file names keep their exact former shape.

`tools/dist.sh` is new: platform from `uname -s` (`Linux`, `Darwin`, `MINGW*`/`MSYS*`, anything
else refused), version parsed from `project(... VERSION ...)`, the short commit appended when
`GITHUB_ACTIONS` is `true` and `GITHUB_REF_TYPE` is not `tag`, the eleven licence files in one
function, an `INSTALL.txt` per platform, `tar.gz` on Linux, `ditto -c -k --keepParent` on macOS
(Apple's own archiver for bundles, which the signing job will reuse after stapling), `7z` with a
`zip` fallback on Windows. Besides the no-argument form it offers `name`, `version`, `stage <dir>
[<from>]` and `archive <dir> <out>`, so that `package.sh` can stage the validated bundle from
`artifacts/vst3`, append its validation lines to `INSTALL.txt`, add `BUILD-RECORD.txt`, and only
then archive. The archivers run inside the staging directory with relative paths so that no
absolute POSIX path crosses into a native Windows program. The macOS `INSTALL.txt` carries a
`Signing:` line that says the bundle is unsigned and how to clear the quarantine attribute;
`tools/macos-sign.sh` (M3) will rewrite that line.

`tools/package.sh` now takes the binary archive from `dist.sh` and names its three archives
`kickcrafter-fable-<version>-...`. Neither `package-preflight.sh` nor `package-negative-controls.sh`
read the archive name (checked with `grep -n kickcrafter-fable tools/`), so they needed nothing for
the rename. I did add `run` to the archived paths of the source archive, the preflight's clean-tree
list and the negative controls' scratch copy: the guide says everything goes through `./run`, CI
will depend on it, and a source archive without it could not follow its own documentation. This is
a small widening of the seam list, recorded here for the reviewer.

`CHANGELOG.md` has the 1.4.0 entry dated from `date +%F` (2026-09-20). `CLAUDE.md` states the three
platforms and the validation asymmetry in its closed decisions, names them in its first line and
lists `./run dist` among the pieces. `docs/development.md` describes `dist.sh` next to the

`.github/workflows/release.yml` runs on tags `v*` and on `workflow_dispatch`, with

`stapler validate`, all teed into `GITHUB_STEP_SUMMARY`. Without an identity it signs ad hoc
(`codesign --force --deep --sign -`), skips notarization, rewrites the `Signing:` line into a
capitalised warning with the `xattr` command, lets `spctl` reject, and prints the warning in the
summary. No `set -x`; no secret is echoed; the notarytool password goes on its command line as
in the references. The script is bash 3.2 (arrays are not used, `eval` checks the variable names).

`tools/dist.sh` now writes its macOS signing note on one line so that the script can replace it.

package (`--type install`) and not a disk image (`--type open`), so no `spctl` invocation is a
meaningful gate for a bare plug-in bundle, and gating on one could reject a correctly signed and
notarized release. The script now gates on `codesign --verify --deep --strict` in every mode and,
when signed, on `codesign --verify -R="notarized" --check-notarization` and `xcrun stapler
validate`; `spctl --assess --type install` is still printed in the summary, labelled "diagnostic
only", never fatal. Decision 10's "spctl verdicts printed in the job summary" is met as printed
output; it cannot be met as a gate, and this is the constraint for the owner: Gatekeeper's
assessment of a plug-in happens when a host loads it, and CI can only prove the signature, the
notarization ticket and the staple. The guide's "Releases" text and its step 2 say the same.
