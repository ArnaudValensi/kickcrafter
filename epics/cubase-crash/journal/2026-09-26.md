# 2026-09-26: T1, the Cubase sequence on Linux; T2 written

The tester's report gained two facts today: Cubase 11, probably Windows 10, and the crash at the
opening of the plug-in, with a message too brief to read before the whole host dies. The brevity
rules out an assertion of ours (there is none compiled in Release; the two `jassert` of the
plug-in are empty there, the engine has none) and the moment rules out the scan (Cubase scans in
a separate sentinel process and blocklists what crashes there). It is the editor, and the most
Cubase-specific thing that happens when an editor opens on Windows is the content scale factor of
a screen above 100 % followed by a size negotiation against an editor that insists on a fixed
aspect ratio. That was the first hypothesis, and the first way to test it was already in the
repository: `kcf_vst3_host` drives the real module through the public VST3 interfaces, on Linux,
where JUCE's `setContentScaleFactor` runs the same code as on Windows apart from a Cubase 10
special case.

The host now asks the view for `IPlugViewContentScaleSupport`, applies 1.25, 1.5, 2.0 and 1.0,
after each applies the size the view reports, then proposes four sizes the constrainer must
correct and re-checks each corrected size as a fixed point of `checkSizeConstraint`. The frame
keeps a budget of sixteen `resizeView` callbacks per factor: past it, it refuses and the run
fails, so a ping-pong is a failure and not a hang, and a recursion would kill the process, which
is the point. Two cycles on the staged 1.5.3 module: sixteen factors, sixty-four negotiations,
twenty host resize requests in total, no refusal, no crash, 58 971 checks passed. The hypothesis
does not hold on the JUCE side, at least. What the test cannot reach is the Windows peer under
per-monitor DPI awareness, which is where way 2 and way 3 take over.

Way 2 is written but unproven: editorhost from the same SDK checkout, in its own build tree
with the hosting examples on (the validator's tree has them off, they need gtkmm on Linux, so
editorhost is macOS and Windows only), and a probe script whose pass is "still alive after
twenty seconds with the editor open". Its alive and dead paths were exercised with two fake
hosts, one that sleeps and one that exits 3: the first passes, the second fails with 3. The
honest limit is that the runners' screens are at 100 %, so editorhost on CI covers Steinberg's
attach and negotiation code, not the DPI factor.

The owner also decided, on the way, that the `%` menu will go and the fixed aspect ratio with it:
the editor is vector-drawn, resizing continuously is enough, and an editor that accepts any size
leaves a host nothing to disagree with. That is T4, after T2 has run.
