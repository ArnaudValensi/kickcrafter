# 2026-09-25: M1, the tools and the workflow

The tester's report arrived with no host name, no moment and no dump, and the honest answer to
"how do we test on Windows" was that nothing did: CI compiled and ran the engine tests, which
never load the bundle. The owner chose to start with the checks that need no host, so this
session built them.

The two validators went into one script, `tools/fetch-validators.sh`, because they share a
shape: fetch something pinned under `external/`, print an executable, do nothing when it exists.
The Steinberg validator is built from the SDK at `v3.8.1_build_84`, the same generation the
development machine validates with. Its configure failed twice on this machine before it passed,
and both failures are the reason the script now turns three SDK options off: VSTGUI wants
`xcb-cursor`, the editorhost example wants `gtkmm-3.0`, and neither is needed by the validator,
whose directory the SDK adds unconditionally. A runner would have hit the same walls. pluginval
is the release binary, 1.0.4, unzipped; on macOS `ditto` instead of `unzip`, to keep the
application bundle's structure.

`tools/validate-bundle.sh` was rewritten rather than patched: it had the Linux module path and
`sha256sum` and `%N` hard-coded, and it now finds the module by platform, hashes with `shasum`
when `sha256sum` is absent and pads the timestamp when `date` has no nanoseconds, as
`run-logged.sh` already did. It falls back to `external/validator/` when `KCF_VALIDATOR` is unset
and nothing is on `PATH`; the fallback was exercised with the variable emptied, 47 tests passed,
and the log header records the new tool's hash (`03e0ad7c...`) instead of the machine's
(`e10440ed...`). `tools/pluginval.sh` mirrors it; strictness 5 passes on the staged 1.5.3 bundle
under the tests' display, with pluginval's own report under `artifacts/logs/pluginval/`.

The MSVC symbols are the only change to `CMakeLists.txt`, under `if(MSVC)`, with the `.pdb`
directed to `build/symbols/` so `dist.sh`, which copies the bundle whole, cannot ship them. The
Linux module was rebuilt with the committed file and with the edited one: `a7f6deaad9190337`
both times, so the edit is neutral on Linux by evidence, not by reading. (The staged module's
hash before this session's first rebuild was `be0213043c290bd4`; the difference comes from that
rebuild, not from the edit, since the two builds around the edit agree. Whether a full
reconfigure is byte-stable across days is a question for another day; the comparison that
matters here is the one with the edit as the only variable.)

`./run check` is green, `./run package-controls` too; `./run preflight` refused before the commit
because the archived scripts were not committed, which is what it is for. The workflow steps are
written but unproven until the manual run of M2.
